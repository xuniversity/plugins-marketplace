# Delegate To Claude

当用户明确要求将任务委托给本机 `claude` 命令执行时，启用本技能。

本技能是一个独立的“执行委托器 + 验收器”，不依赖任何特定工作流或其他技能。

## 核心职责

1. 由 Codex 组织委托上下文，而不是把任务原样转发给 Claude。
2. 通过本机 `claude -p` 的 headless 模式在真实环境中发起非交互委托。
3. 要求 Claude 将状态、原始输出和最终结果落盘到统一目录，而不是只依赖终端最终输出。
4. 要求 Claude 返回结构化结果。
5. 由 Codex 对 Claude 的产物进行二次检查、复跑验证并决定是否接受结果。

## 运行环境硬规则

1. 委托 Claude 时，默认必须在 Codex 沙箱外的真实环境中运行，不将沙箱内调用作为正式路径。
2. 委托 Claude 时，默认使用宽权限模式，避免无头模式因权限确认而卡住。
3. 只有在当前仓库是可信工作区时，才允许使用宽权限模式。
4. 一旦委托已成功启动，Codex 不得因为短时间内缺少终端输出而直接终止 Claude 并自行接管实现。
5. 如果委托启动后仍无法观测完成状态，应报告 `blocked`，而不是静默 fallback 成由 Codex 本地实现。

## 使用边界

### 适合委托的场景

1. 用户已明确要求“委托给 Claude Code”或“使用 delegate-to-claude 技能”。
2. 当前任务边界清晰，且主要是实现、修改、补测试、运行验证。
3. 已存在可执行计划，或用户直接给出了足够明确的实现任务。
4. Codex 能够清楚界定允许修改的文件范围、验证命令和成功标准。

### 不适合委托的场景

1. 需求仍处于探索或方案发散阶段。
2. 当前任务需要大量新的架构决策，而这些决策未在上下文中被批准。
3. 当前计划过于粗略，无法提炼出可直接施工的执行步骤。
4. 无法定义验收标准，或无法从本地复核 Claude 的执行结果。

遇到以上场景时，不要强行委托；应先补足计划或直接由 Codex 继续处理。

## 两种运行模式

### 模式 1：计划驱动模式

用于“已有计划文件或明确实施方案”的执行场景。

执行原则：

1. 由 Codex 先定位并读取计划文件。
2. 默认不要让 Claude 自行搜索计划文件。
3. 优先将“当前要执行的计划步骤 + 关键约束 + 验收标准”作为 prompt 输入 Claude。
4. 只有在明确受益时，才把一个已知的本地计划文件路径告诉 Claude 让其读取；禁止让 Claude 自行在仓库中发现计划。

在本模式下，Codex 负责：

1. 找到已批准计划。
2. 提取当前待执行步骤。
3. 根据任务复杂度补充必要上下文。
4. 明确允许修改的文件、禁止行为和验证命令。

### 模式 2：显式任务模式

用于脱离任何工作流的独立委托。

适用条件：

1. 用户直接给出明确的实现任务。
2. 任务可以在不依赖计划发现流程的情况下直接实施。
3. Codex 能直接列出目标、约束、修改范围和验证方式。

## 委托上下文分层

为节省 Codex 自身上下文与 token，本技能要求由 Codex 先判断复杂度，再选择补充档位。

### 精简档

适用于小任务、边界清晰、上下文缺口很小的场景。

委托内容至少包含：

1. 当前任务或计划步骤
2. 允许修改的文件范围
3. 验收标准
4. 禁止事项
5. 必须遵守的关键实现约束或编码规范摘要

### 标准档

适用于大多数执行任务。

在精简档基础上，再补充：

1. 原始需求摘要
2. 直接相关的代码上下文
3. 关键设计约束
4. 必须执行的验证命令

### 增强档

适用于复杂但仍然可以委托执行的任务。

在标准档基础上，再补充：

1. 已知风险
2. 已排除方案
3. 关键接口、数据结构或依赖约束
4. 更严格的产物边界与验证要求

### 档位选择原则

1. 默认从精简档开始评估。
2. 计划足够细、相关代码影响面小，用精简档。
3. 计划较粗、需要理解业务意图或局部现有实现，用标准档。
4. 修改跨度较大、约束较多、容易偏离边界，用增强档。

## 委托工作目录约定

所有本技能产生的过程文件统一放在：

`.agents/memory-bank/[分支名称]/delegate-to-claude/[功能名称]/`

建议至少包含：

1. `prompt.txt`
2. `status.json`
3. `result.json`
4. `raw-output.jsonl`
5. `launcher.log`
6. `command.txt`
7. `launcher-meta.json`
8. `summary.md`

目录命名要求：

1. `[分支名称]` 使用 `git branch --show-current` 的结果。
2. `[功能名称]` 建议采用 `YYYY-MM-DD-功能slug` 格式，例如 `2026-06-05-breakout-single-html`。
3. 如果同一天同名功能发生冲突，追加编号后缀，例如 `2026-06-05-breakout-single-html-02`。
4. `slug` 使用小写字母、数字和连字符，避免空格、中文和临时缩写。
5. 不要把这些过程文件散落到仓库根目录或其他业务目录。

## 委托前检查

在调用 Claude 前，Codex 必须先确认：

1. 当前任务是否真的需要委托，而不是自己更快完成。
2. 任务边界是否清晰。
3. 是否已有明确的成功标准。
4. 是否能在本地验证 Claude 的修改。
5. 当前仓库是否可信，适合使用 headless 委托。
6. 是否已确定本次委托的统一工作目录。

如果这些条件不满足，应拒绝委托或先补充上下文。

## Claude Prompt 组织要求

委托给 Claude 的 prompt 应尽量稳定，建议包含以下区块：

1. 角色说明：你是执行代理，只能实施，不做额外设计。
2. 仓库上下文：当前工作目录与允许访问范围。
3. 委托工作目录：Claude 必须写入哪些状态与结果文件。
4. 任务来源：计划步骤或明确任务描述。
5. 任务目标：本次需要完成什么。
6. 允许修改范围：文件、目录、模块。
7. 禁止事项：不得扩展需求、不得计划外重构、不得修改越界文件。
8. 实现约束摘要：仅包含当前任务相关约束。
9. 验证要求：必须运行哪些命令，或至少验证什么。
10. 输出契约：必须返回 JSON。

输出契约请参考 [references/output-contract.md](references/output-contract.md)。
通用 prompt 模板请参考 [references/prompt-template.md](references/prompt-template.md)。

## Claude 返回结果的最低要求

Claude 的最终输出必须是一个 JSON 对象，至少包含：

1. `status`
2. `summary`
3. `files_changed`
4. `commands_run`
5. `verification`
6. `risks`

如果 Claude 无法完成任务，必须返回 `blocked` 状态，并说明阻塞原因，而不是自行改变方案。

除终端最终输出外，Claude 还必须按委托目录协议写入 `status.json` 和 `result.json`。

## 调用方式

优先使用本技能附带脚本：

`[skill目录]/scripts/run_claude_delegate.sh`

脚本职责：

1. 统一封装 `claude -p` 的调用细节。
2. 默认使用流式输出，增强可观测性。
3. 固化 `--` 分隔，避免 prompt 被 `--add-dir` 参数吞掉。
4. 将原始输出、命令快照和启动日志写入统一委托目录。
5. 以宽权限模式启动 Claude，减少无头模式下的权限阻塞。
6. 使用 `stdin` 喂入 prompt，避免 `command.txt` 因内联长 prompt 出现乱码和不可读问题。

## Codex 的验收义务

Claude 返回成功并不代表任务已经完成。Codex 必须继续执行以下动作：

1. 检查改动文件是否越界。
2. 检查是否存在计划外修改。
3. 复读关键文件，确认实现与约束一致。
4. 复跑关键验证命令。
5. 结合当前任务约束和项目规则进行复核。
6. 向用户报告“Claude 已执行”与“Codex 是否验收通过”这两个独立结论。

如果 `status.json` 已表明 Claude 接单执行，而 `result.json` 尚未出现：

1. 不要直接杀掉 Claude 并自行实现。
2. 先检查 `summary.md`。
3. 再检查 `raw-output.jsonl` 与 `launcher.log`。
4. 如需要，最后查看 `command.txt`、`launcher-meta.json` 和 `prompt.txt`。
5. 如超过预设等待窗口仍未完成，报告 `blocked` 或等待用户决定，而不是静默接管。

## Codex 最终验收清单

最终验收由 Codex 负责，Claude 只负责执行，不负责最终裁决。

至少检查：

1. `status.json` 是否为完成态，且无明显异常状态回退。
2. `result.json` 是否存在，且为合法 JSON。
3. `summary.md` 是否指向了正确的结果文件和日志文件。
4. Claude 报告的 `files_changed` 是否全部位于允许修改范围内。
5. 是否存在计划外修改、越界文件修改或未授权新增文件。
6. 关键验证命令是否由 Codex 复跑并通过。
7. 交付产物是否符合原任务目标与约束。
8. 如存在本地 hook、副作用命令或额外日志，是否已确认未污染业务结果。
9. 只有以上检查通过，才能向用户报告“Codex 验收通过”。

## 推荐的用户触发语义

以下语义均应触发本技能：

1. “使用 delegate-to-claude 技能”
2. “委托给 claude code 执行”
3. “使用 Claude headless 实施任务”
4. “将当前实现任务委托给 claude code 实施并验证结果”

## 失败处理

当出现以下情况时，应明确报告，而不是伪装成功：

1. 本机 `claude` 命令不可用
2. 当前环境不允许 Claude headless 正常运行
3. 计划内容不足以支撑执行
4. Claude 返回结果无法解析
5. Claude 完成了修改，但 Codex 验收未通过
6. Claude 已启动，但长时间未写入 `result.json`

## 简要工作流

1. 判断当前使用模式：计划驱动或显式任务
2. 收集并压缩任务上下文
3. 选择补充档位：精简 / 标准 / 增强
4. 创建统一委托工作目录
5. 参考通用模板生成 Claude prompt，并写入 `prompt.txt`
6. 在真实环境中调用脚本发起 headless 委托
7. 观察 `status.json`、`raw-output.jsonl` 和 `result.json`
8. 读取 Claude 结果
9. 由 Codex 复核并决定是否接受
